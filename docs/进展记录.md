## 8. M1.1 —— M1 真机日志暴露的三个真实问题（已修，已部署）

这一轮**没有改任何设计/规则**，只修"日志证明代码写错了"的地方。

### 8.1 ★ `GenderWeights` 的类型被交接文档写错了（功能 bug，旧 MOD 同样存在）

**交接文档第 12 节写的是 `int[3]`，实测（反射）是 `System.Collections.Generic.List<int>`。**

```powershell
tools\probe_api.ps1 -Type BattleTech.PilotGenerator
#   GenderWeights : System.Collections.Generic.List`1[[System.Int32, mscorlib, ...]]
```

后果（日志实证，13 条）：

```
[GenderRatio] 设置性别刷出比例失败（不影响其它功能）：Specified cast is not valid.
```

`(int[])_weightsField.GetValue(...)` 在**这个表被游戏建出来之后**每次都抛
`InvalidCastException`，被外层 catch 吞掉 ⇒ 常量那一步（`SetInt`）也被跳过 ⇒
**"改比例立即生效"悄悄失效**，只有表还是 `null` 的那一次真正生效。
因为常量在第一次就写对了、"表"又是照着当时的常量建的，所以**表面上一切正常**
（用户当时也确实说功能正常）—— 属于最难发现的一类 bug。

修法：`OverwriteLive(object, int[])` 同时支持 `IList<int>`（实测类型）与 `int[]`（兜底），
遇到别的类型只警告一次并说明"要等表重建才完全生效"。

> **推广**：交接文档 §12 那张"已实测 API 真值表"里凡是靠 `iltool.py` 读出来的
> **字段类型**都不要直接信（`iltool.py members` 根本不解析字段类型，会打印 `?`）。
> 字段/属性/方法签名的真值请用 `tools\probe_api.ps1`（运行时反射）。

### 8.2 滑块手柄用的是**取不到的内置资源**（外观缺陷，旧 MOD 同样存在）

```
Unity [ERROR] The resource UI/Skin/Knob.psd could not be loaded from the resource file!
Unity [ERROR] The resource UI/Skin/UISprite.psd could not be loaded from the resource file!
（各出现两次 = 两个滑块 × 两次尝试）
```

`StepSlider.AddCircleSprite` 取 Unity 内置皮肤 `UI/Skin/Knob.psd`，**正式版游戏里没有这些资源**
⇒ `sprite = null` ⇒ 手柄画成**方块**（轨道也是方角矩形）。
修法：`StepSlider` 自己用 `Texture2D` + `Sprite.Create` 程序生成
**圆形**（手柄）与 **9 宫格圆角矩形**（轨道 / 已填充段）贴图，`Image.type = Sliced`。
⇒ 零资源依赖，`output_log.txt` 也不再被污染。

### 8.3 ModLoader 传进入口的 `mod.json` 文本拿不到（只影响日志文字）

M1 日志：`mod 名称=GenderRatio，目录名=PilotCombined` —— 目录名对、名称退回了写死的默认值，

我给 `build.ps1` 加了两行**中文注释**，结果 `build.ps1` 直接报
`The term '-RedirectStandardOutput' is not recognized`。
根因：Windows PowerShell 5.1 读**无 BOM** 的 `.ps1` 时按系统 ANSI(GBK) 解码，

⇒ **`build.ps1` 永远保持纯 ASCII**，所有中文放 C#/JSON 里（这条原文件头部就写了，我又犯了一次）。
配套：用 `Start-Process ... -RedirectStandardOutput` 代替 `& exe 2>&1`，
否则子进程往 stderr 写一行就会被 `$ErrorActionPreference = Stop` 变成终止性错误、真正的测试输出反而不见了。

另外测试 exe 在 `%TEMP%` 里跑，**必须把 `Newtonsoft.Json.dll` 拷到它旁边**，
否则一碰 `JObject` 就报"无法打印异常字符串"这种毫无线索的错。

### 15.6 ⚠️ 第一次真机：格子数对了但**图没换** —— 根因是"协程没有跑"

用户反馈（截图）：格子数已经正确（男性 12 格 ✅），但**格子里的图仍然是原来的哈希图**
（男女混杂、还有重复、「他们」里还是只有 1 张仿生人）。

**根因（很隐蔽）**：`PortraitSelectorElement.RenderThumbnail()` 和 `SetData(...)` 的返回类型是
**`IEnumerator`（协程）**：

```
Void   ...（无）
IEnumerator  RenderThumbnail()
IEnumerator  SetData(PortraitSettings portraitSettings)
```

而 15.3 里我写的是 `el.RenderThumbnail();` —— 那只是**构造了一个迭代器然后丢掉**，
协程体**根本不会执行**（必须交给 `StartCoroutine`）。所以"改完映射再强制重画"这一步**从来没发生过**，
格子一直显示首次渲染时（按哈希）贴上去的那张图。

**修法（两层，第二层是关键）**：

1. `el.StartCoroutine(el.RenderThumbnail())` —— 真正让游戏的协程跑起来；
   （反汇编 `<RenderThumbnail>d__16::MoveNext` 确认：协程体里就是调
   `PortraitManager.GeneratePortraitTexture` + 把结果贴到 `RawImage`。）
2. ★ **不再依赖游戏的渲染时序**：`PortraitSelectorElement.thumbnail` 的真实类型是
   `UnityEngine.UI.RawImage`，所以**每帧直接把指定的那张贴上去**
   （`img.texture = PortraitRegistry.GetHandout(settingsId, image, 128)`）。
   谁覆盖了我们，下一帧就盖回来；贴图来自我们自己的缓存（每次取用前验活、被销毁会自动重建）。

同时把"已指定哪些格子"打进日志（前 3 个 `settingsId → 图片` 的例子），便于验证。

> 这次踩坑的推广教训：**看到方法返回 `IEnumerator` 就必须 `StartCoroutine`**；
> 而"让游戏重画"这类做法永远要兜一层"我直接写最终状态"，因为时序与缓存不在我们手里。

**真机验证通过（10/15）**：用户确认「他」12 格、「她」59 格、均无重复、「他们」75 格含 4 张仿生人。
另外确认：**图片数不是写死的，每次启动自动扫描目录**；唯一上限是游戏列表只有 90 格
（单池超过 90 张时多出来的上不了选择列表，但随机驾驶员仍会用它们，日志有 WARN）。

## 17. 10/15 第二次真机（移走 `portraits\male`）：三个问题的定位与修复

用户的实验：把 `portraits\male` 整个移出 `portraits\` 后重启，进角色创建界面。结果：
① 「他」确实从代词选择器里消失了 ✅（M8 生效）；② **女性列表里冒出仿生人、「他们」里又找不到仿生人**；
③ **F9 窗口该锁的滑块/勾选框没有锁**。

### 17.1 「女性列表里冒出仿生人」：残留旧指定 + 可见集合变化

这是真 bug，根因有两层：

1. **残留指定**：`ClearGalleryOverrides` 只在离开创建界面时才调用，所以"上一轮给隐藏格子写过的指定"
   会留着。先在「他们」里给 63 个格子指定过图（含 4 张仿生人），切到「她」时只重算前 59 格，
   第 60~89 格仍带着旧指定（其中就有仿生人）。一旦游戏重排元素顺序
   （`PopulateList` 的 `GetRandomizedSortOrder` / 元素池化复用），
   这些"带仿生人旧指定"的格子就可能变成可见格子。
2. **根本没有指定的格子**：元素是 `Spawn` 出来后才由 `SetData`（**也是协程**）填 `portraitSettings` 的，
   所以列表刚填完的那一瞬间，靠后的元素可能还读不到预设 id ⇒ 我们的循环 `continue` 跳过了它们 ⇒
   这些**可见但没被指定**的格子显示的是"按预设自身性别哈希"的图。而当一个性别的池子为空时，
   那条路的兜底是 `CandidatesFor` 的最后一句 **`return Pool`（整池任取）** ——
   男池空了 ⇒ 男性预设的格子可以从"整池（含仿生人）"里任取 ⇒ **仿生人串进女性列表**。

**修法（三层，都在 `PortraitGalleryFilter`）**：

| # | 修法 | 作用 |
|---|---|---|
| 1 | **每帧一致性检查**：可见格子显示的必须正好是"当前池子的第 i 张"（`_assigned[id] == pool[i % n]`），不一致立刻重算 | 自愈：顺序变化、残留指定、迟到初始化都会被下一帧纠正 |
| 2 | 重算时**先 `ClearGalleryOverrides(null)` 清掉所有旧指定** | 不给隐藏格子留残留 |
| 3 | **读不到预设信息的格子直接隐藏**（而不是跳过并显示不受控的图） | 宁可少一格，也不显示一张我们控制不了的图 |

### 17.2 「他们」里找不到仿生人：注意它在列表**最后**

## 18. ⚠️ M8 的"删掉代词选项"被真机证伪 —— `get_gender()` 是**按下标**算性别的

### 18.1 现象（用户 10/15 第三次真机，男池仍为空）

* F9 窗口的灰化**已生效** ✅（17.3 的补充起效了）；
* 但创建界面里：**「她」= 46 项、里面混着仿生人**；**「他们」= 59 项、全是女性图、没有仿生人**。
* 用户直接反问："是不是整反了？"—— **是的，而且是我的 M8 实现造成的。**
* 用户补充：把男性肖像加回来再重启，一切正常。（三项俱全时我们不动选项，映射就是对的。）

### 18.2 根因：`get_gender()` 用 `selectionIdx`，不是用文字

```
SGCharacterCreationNamePanel::get_gender
    0x0001 ldfld  pronounSelector
    0x0010 ldfld  pronounSelector
    0x0015 callvirt HorizontalScrollSelector::get_selectionIdx      ← 选项【下标】
```

`LoadOptions()` 则是 `SetOptions(new[]{ hePronoun, shePronoun, theyPronoun })` ⇒ 规范顺序是
**[他(0)=Male, 她(1)=Female, 他们(2)=NonBinary]**。

16.2 里我用 `SetOptions(keep)` **删掉了「他」**，列表变成 `[她, 他们]` ⇒
**下标 0（显示"她"）被游戏当成 Male、下标 1（显示"他们"）被当成 Female**。于是：

| 用户选 | 游戏实际判定的性别 | 我们的池子 | 结果 |
|---|---|---|---|
| 「她」 | **男** | `portraits\male` 为空 ⇒ 旧代码"什么都不做" | 90 项按预设自身哈希取图 ⇒ 串进仿生人 |
| 「他们」 | **女** | `PathsOf(Female)` = **59 张** | **59 项全是女性图、无仿生人**（与用户数到的数字一致） |

### 18.3 修法：**不删选项**，改成"池子为空 ⇒ 退回全部图片"

1. **撤掉代词选项裁剪**：`PrunePronounOptions()` 保留作参考但**不再调用**
   （代码里留了醒目注释 + `EnablePronounPruning` 说明为什么不能这么做，避免以后有人又打开）。
2. **替代做法**（`PortraitGalleryFilter.Poll`）：代词对应的池子为空时，
   把列表池子换成 `AllPaths()`（**全部图片**）并打 WARN：
   `代词=男 对应的图片池是空的（portraits\male）⇒ 本次退回『全部图片』（N 张），让你仍然能正常挑图`
   —— 列表照常可用、每张图都能选到，且**不会**让下标错位。
3. 因此"选性别时藏掉无图性别"这条需求**放弃实现**（技术上不安全）。
   替代保障：`肖像池优先`（M5）已经保证**新生成的驾驶员只会有图的性别**；
   F9 窗口的池子状态行也会写明"该性别没有肖像"。

### 18.4 教训

**动游戏 UI 的"列表/选项"之前，必须先确认游戏是"按文字"还是"按下标"消费它。**
这一次 IL 就在手边（`get_selectionIdx`），但我上一版只确认了"有 SetOptions 可用"就动了手 ——
而 `SetOptions` 能改的是**顺序与数量**，恰恰是下标语义最敏感的两件事。

## 20. 勾选标记：把"斜杠"改成真·对勾

用户反馈：勾选框里的标记看起来像**斜杠**，希望改成**对勾或圆点**。

原因：旧实现是用一个 `14×3.5` 的 Image 旋转 −45° **近似**勾号 —— 只有一笔，当然是斜杠。

改法（`GenderRatioWindow.TickSprite`）：**程序生成一张对勾贴图**，做法与滑块圆形手柄同一套路子 ——
对 32×32 的每个像素求它到两段线段的**最近距离**，小于半线宽就填、边缘 1 像素做渐变（抗锯齿）：

```
起点 (4,16) → 折点 (12,7) → 终点 (28,26)     半线宽 2.8
```

* 为什么不"两个旋转矩形拼"：拼法在两段接缝处会露缺口、大尺寸下有锯齿；
  距离场一次成型、边缘干净，而且形状参数集中在一处好调。
* 勾号 Image 尺寸 `22×22`、在 24×24 的方框里居中；颜色仍由 `Image.color` 叠加，
  所以**变灰逻辑不变**（勾号、方框、文字一起变暗）。
* 想换"圆点"只需把 `tickImg.sprite` 换成实心圆贴图（几行），留着以后按需改。

### 22.7 ⚠️ 第一次真机：把游戏切成英文后窗口仍是中文 —— 抽样兜底**误判**

2. **抽样只在"语言设置读不到或 UNDEFINED"时才启用**，阈值从 25% 提到 **≥80%**；

4. 新增**手动强制**：`combined.json` → `popup.ui_language` = `auto`（默认）/ `en` / `zh` / `de` / `ru`

> 教训：**兜底信号不能无条件覆盖主信号**。要覆盖，必须先满足"主信号不可用"这个前提；
> 否则一旦兜底信号的判据不严谨（本例：汉化词典仍在被统计），它就会把正确的结论翻错。

| ③ 键一致性 | 窗口用到的 `Loc` 键 与 `Loc.cs` 表里的键对账（防拼错 → 会显示键名；防漏建/多余） |

**工具自身也修了一个 bug**：取 C# 字符串字面量的正则没处理转义（`\"`、`\\`），
带转义的字符串会让匹配**错位**，后面的字面量全被吞进一个跨行的"假字符串"里
（表现为"键提取几乎全丢"，只有 1 个键被认出来）。现在用能处理转义的正则
`"((?:[^"\\]|\\.)*)"`。当前三项全 OK。

## 23. 怎么加一门新语言（不用改代码、不用重编译）

### 23.1 位置：`<mod>\loc\<语言代码>.json`

```
PilotCombined\
    loc\en.json     英文（内置真值导出）
    loc\zh.json     简体中文
    loc\de.json     德文（当前是英文占位，等翻译）
    loc\ru.json     俄文（同上）
```

文件形如：

```json
{
  "//": "注释键，会被忽略（和 combined.json 的习惯一致）",
  "win.title": "Pilot Spawn Ratio",
  "chk.other": "Enable \"{0}\"",
  "pool.line1": "Portrait pools: F {0} / M {1} / {2} {3}  (total {4})"
}
```

* **加语言**：放一个 `loc\xx.json` → 在 `combined.json` 里把 `popup.ui_language` 写成 `xx`
  （或让自动判定命中）→ 重启即可。**不需要改代码、不需要重新编译。**
* **优先级**：`loc\<语言>.json` 的值 > 内置表（`Loc.cs`）> 英文 > 键名。
  缺文件 / 缺某条 → 自动回退，不会出现空白。
* **占位符** `{0}`、`{1}`… 是 `string.Format` 的参数，**翻译时必须原样保留**（个数也不能变）。
* 键拼错时启动日志会点名：`⚠ 有 N 个键在内置表里不存在（可能拼错）：…`
* 文件名目前支持 `en / zh / de / ru`（对应 `Loc.Code()`）；要再加一门语言，
  在 `Loc.Lang` 枚举 + `Loc.FromCode/Code` + `Loc.Detect` 的映射里各加一行即可（三行）。

### 23.2 自动生成/同步语言文件

`tools\dump_loc.py`：解析 `src\Loc.cs` 的 `Add/Add4` 表，导出上面四个 JSON。
**改过内置表就重跑一次**，保证 JSON 与代码不脱节（手抄 36 条键必然会飘）。
`en/zh` 导出真值，`de/ru` 导出英文占位（翻译者只需替换值）。

部署：`build.ps1` 会把 `mod\loc\` 整个拷进部署目录 ✅。

### 23.3 关于"游戏语言下拉里俄文显示成方块"

**与本 MOD 无关**，是**字体缺字形**（tofu）。依据：

* 游戏按语言切换字体（`Localize.FontLocalizationManager.ConvertFontForCulture` +
  `Localize.FontLocTable` 就是干这个的）；
* 你的中文来自 **BTHanHua / BTHanHuaFont** 两个 MOD ⇒ 中文激活时用的是它的中文字体；
* 截图里 `English / Deutsch / Français / 中文` 都正常，**只有 `Русский` 是方块** ⇒
  不是整体字体失效，而是**当前字体没有西里尔字形**；
* 本 MOD 只读游戏字体（`font_file` 留空时从场景借一个来画自己的窗口），**从不修改游戏字体**。

验证方法：把游戏语言切成 English（或临时移出 `BTHanHuaFont`）再打开这个下拉 ——
俄文应当正常显示（游戏本体支持俄文，必然带西里尔字体）。
若确认如此，属于汉化字体的字形覆盖问题，可反馈给汉化作者；对我们只是"下拉里一个标签"，
不影响功能。
